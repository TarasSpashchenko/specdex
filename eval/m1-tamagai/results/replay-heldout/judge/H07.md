**Question:** What should a kid see if their phone hasn't been able to pick up our latest settings for over a month?

**Gold answer:** The accepted amendment says to keep the last good configuration file. The inability to fetch it for more than 30 days does not itself change anything the child sees.

## Answer A

The kid should see the usual Pip experience: settings being over a month old must not by itself change the child view. The phone keeps the last valid settings, or bundled defaults if none exist; caps, consent, security restrictions and the guaranteed date still apply, and an unseen extension cannot be assumed. If a separate condition stops talk, Pip shows folded “resting ears” and keeps playing with basic-mode features; the cause is explained only to the parent.

## Answer C

The child should see nothing different. If a phone can't fetch the latest settings, it keeps using the last good configuration file, and fetch age alone never changes what the child sees. A fetch that fails, a bad signature, or an unknown `schemaMajor` all leave that last good file in place. If the phone has never had a good file, it uses the bundled defaults and doesn't assume any extension it hasn't received.

Caps, consent, security restrictions and the guaranteed date still apply on their own terms, so they aren't affected by staleness. The only child-facing case in the specs where the child sees something different (resting ears, with basic mode continuing) is an old app excluded for a documented security risk. That is a different situation from a stale fetch.

I didn't find any spec text that gives the child a "settings out of date" notice. Notices about configuration go to parents as a dismissible status card.

## Answer D

The child should see nothing different. Under AD-16, fetch age alone never changes what the child sees. The device keeps using the last good signed configuration, or the bundled defaults if it has never had a good one. Caps, consent, security restrictions and the guaranteed date still apply on their own terms. An extension that was not received is never assumed. The 30-day figure is the interval at which devices should fetch when they can connect, not a cutoff after which the child view degrades. The addendum's interface table also gives "Last good file" as the offline behavior for the global configuration. The UX spec says the child view is identical for every resting-ears cause. I did not find a spec that defines a separate child-facing "settings out of date" state.
